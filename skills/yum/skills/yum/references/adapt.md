# Yum adapt

Turn an inspected reference into decisions that work for this product.

## Inspect both sides

Read the reference and the target's relevant components, tokens, content, and constraints. Use supplied screenshots or recordings directly; use a browser for named live pages. Distinguish observed details from inference. Do not describe an inaccessible reference from memory.

Match the requested fidelity. A user-owned design, licensed template, or explicit reproduction task may call for close implementation. A request for inspiration usually calls for transferable structure and an original surface. Do not impose arbitrary divergence or a three-reference requirement. Respect the user's rights and stated authorisation; a gallery link alone does not establish asset reuse rights.

## Make the translation explicit

Read [translation.md](translation.md) for the relevant design dimensions. For each important choice connect:

`observed reference feature → useful purpose → target-specific decision → validation`

Examples: dense navigation becomes the target's own information hierarchy; a strong type contrast uses its existing font roles; a scroll narrative maps to its actual content and reduced-motion path. Copy, data, assets, and interaction rules must come from the task rather than a competitor's fictionalised equivalent.

Retain the user's existing requirements, commerce rules, and navigation unless the brief changes them. Do not let a reference's layout silently remove a necessary state or action. Reuse local components for repeated patterns. Introduce a new tool or dependency only when the requested result needs it.

If the reference is unavailable, continue work supported by the target and supplied evidence. Label any independent direction as a proposal. If matching that specific reference is essential, state the missing evidence and do not claim fidelity. Lack of browsing does not forbid original design.

## Produce the requested artefact

For a brief, deliver a buildable structure with content, states, tokens, and acceptance criteria. For implementation, make the changes and inspect the rendered result at relevant sizes and interaction states. For assets, finish and inspect the requested set in its required formats. Do not substitute a research report for an authorised build.

Check both visual relationships and target requirements. Attribute references in the handoff with what was adopted or changed; user-facing product credits belong only where required or requested. Report what was verified and any fidelity or runtime gaps. Never claim that a screenshot establishes accessibility, motion, or production readiness.
