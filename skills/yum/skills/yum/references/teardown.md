# Yum teardown

Compare how references solve the same job, then explain which choices fit the user's product.

## Establish comparable evidence

Use the supplied references first. If discovery is needed, choose sources suited to the job: production screen libraries for app UI, journey recordings for flows, live sites for marketing, and official documentation for component behaviour. Prefer a few relevant peers over a large moodboard. A named single-reference teardown does not require finding extra peers.

Read [comparison-lenses.md](comparison-lenses.md) for the relevant surface. Inspect evidence with the available browser, connector, or file tools. Record product, source URL/file, platform, capture date when known, inspection date, and state or step. A successful homepage fetch does not prove a specific screen was viewed.

Compare the same task and entry conditions. Call out mismatched platform, user role, authentication state, plan, or capture age. Do not invent intermediate steps, hidden branches, font names, timings, or success rates. A missing frame means unknown; it does not prove the control is absent.

## Extract and judge

Separate three kinds of statement:

- **Observed:** a source-backed fact about the inspected material.
- **Inferred:** an explanation of why the design might work, with its limits.
- **Proposed:** a choice for the user's product.

Describe hierarchy, sequence, action placement, recovery, and content roles. A screenshot supports appearance at its captured size, not keyboard accessibility or responsive behaviour. A concept can inform art direction; label it conceptual unless shipped use is established.

A repeated choice across independent products supports a pattern hypothesis, not proof of effectiveness. Explain meaningful differences; when a recommendation is uncertain, seek a relevant counterexample instead of forcing a fixed reference count. Do not extrapolate a competitor's conversion rate from its layout.

## Deliver a decision

Use a compact comparison when several references are involved. For each recommended pattern, include the job it serves, source observations, conditions where it fits, tradeoff, and adaptation to the user's context. Credit the product or creator and link the actual item, not only the gallery homepage.

Keep proposed states visibly separate from observed states. If evidence is partial, complete the supported analysis and name the unresolved question. Finish with the requested recommendation or brief; implementation requires an implementation request.
